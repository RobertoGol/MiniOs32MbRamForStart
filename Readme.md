# Экосистема CtOs: Спецификация Архитектуры и Порядок Разработки

Проект по созданию независимой, ультра-легковесной вычислительной среды для устройств с ограниченными ресурсами. Целевой испытательный стенд — смартфон Samsung Galaxy A10 (процессор Exynos 7884, 2 ГБ ОЗУ) под управлением прошивки /e/OS, полностью очищенной от сервисов Google.

## 🎯 Главная цель проектирования
Создать быструю, энергоэффективную графическую среду (без использования консоли, но и без тяжелых движков вроде Chromium/Electron) для воспроизведения и поиска музыки без цензуры со стороны коммерческих платформ (Яндекс.Музыка и др.). Оптимизация энергопотребления достигается за счет контролируемых пауз ядра процессора.

## 🛠️ Порядок и Этапы Разработки (Строгая последовательность)

### Этап 1: Спецификация Языка KITII (Папка `Compiler` / `Lang_for_my_decisions-master`)
Разработка грамматики, операторов и концепции типов данных `void` (управление сырой памятью на стыке высокоуровневой логики и регистров).

### Этап 2: Создание Компилятора (`compiler.core`)
Написание лексера, синтаксического анализатора (парсера) и генератора промежуточного байт-кода на основе `main.vc`.
*   **Задача:** Научить систему разбирать код файлов конфигурации и логики, строить абстрактное синтаксическое дерево (AST) и транслировать его в инструкции для рантайма.

### Этап 3: Разработка Модулей Операционной Системы (Папка `CtOs`)
Проектирование низкоуровневых слоев и логики управления «железом».
*   `kernel.ctos` — Главный диспетчер прерываний, планировщик задач и логика энергосбережения (`sys_call sleep`). Модель многопоточности — как в Linux (задачи, вытеснение по таймеру, vruntime-честность, futex-подобные мьютексы), реализация — целиком на KINII: см. `CtOs/SCHED_SPEC.md`.
*   `memory.ctos` — Аллокатор оперативной памяти и таблица распределения регистров переменных.
*   `bridge.ctos` — Аппаратная шина ввода-вывода (I/O) для связи с внешними компонентами.
*   `runtime.ctos` — Изолированная среда выполнения программ.

### Этап 4: Разработка Эмулятора (Папка `CtOs-Emu`)
Создание хост-прослойки для выполнения инструкций ядра CtOs на целевых устройствах и архитектурах (Windows / ARM Android).
*   **Задача:** Реализация бинарного или интерпретируемого моста, который эмулирует аппаратные прерывания клавиатуры, экрана и прокидывает сетевые пакеты через стабильный бэкенд (модуль `yt-dlp`).

### Этап 5: Разработка Приложения CtMusic (Папка `CtMusic`)
Финальная сборка кроссплатформенного плеера-поисковика.
*   **Задача:** Связать интерфейс разметки (`View/index.web` и реактивный слой `View/Rev.web`) с сетевым I/O драйвером эмулятора. Результат — мгновенный поиск, парсинг «паспортов» треков и скачивание MP3 напрямую по ID без цензуры.

## 🧠 Дополнение к Этапу 1: Философия и Компоненты Синтаксиса KITII (Void)
Язык соединяет в себе мощь системного программирования и гибкость прикладных сценариев:
*   **Синтаксическая база:** Строгость управления памятью и указателями C++ + лаконичность выражений Python.
*   **Архитектура памяти (Концепция B/Void):** Бестиповые ячейки данных (`cell:raw`), где тип определяется способом обращения к памяти, что гарантирует максимальную скорость и низкий вес бинарников.
*   **Асинхронность и Сеть (JS/Java/3GPP):** Нативная поддержка событийной модели для реактивного интерфейса (модуль `Rev.web`) и встроенная поддержка протоколов телекоммуникации (3GPP) и USB-интерфейсов (ADB/ADT) для низкоуровневой отладки.
*   **Компиляция:** JIT/AOT-гибрид. Прикладной код может интерпретироваться на лету, а критические модули ядра (`kernel.ctos`) перекомпилируются в чистый ассемблер (ASM) под целевую архитектуру чипа (ARM/x86).

## 🎮 1.1. Архитектурное вдохновение: Концепция PSP Kernel (uOFW / ARK)

Операционная среда CtOs и прикладной слой CtMusic идейно и архитектурно вдохновлены принципами проектирования системного ПО портативной консоли PlayStation Portable (прошивки M33 / PRO / ARK-4). 

Консоль PSP доказала, что операционная система может быть графической, быстрой и реактивной, имея в распоряжении всего 32MB/64MB ОЗУ и процессор на 333 МГц. CtOs перенимает ключевые паттерны этой архитектуры для оптимизации работы на Samsung A10:

*   **Фоновые Системные Модули (PRX-style):** Файлы с расширением `.ctos` (такие как `kernel.ctos`, `memory.ctos`, `bridge.ctos`) работают как изолированные динамические системные модули (аналоги `.prx` драйверов в PSP), которые подгружаются рантаймом только при возникновении аппаратных прерываний.
*   **Прямой Frame-Buffer рендеринг (VSH/XMB-style):** Структура разметки интерфейса `index.web` и реактивный слой `Rev.web` создаются по принципу легковесной графической оболочки XMB. Система полностью отказывается от тяжелых браузерных движков, отрисовывая элементы напрямую через графическую шину хоста.
*   **Изолированные Драйверы Потоков (Inferno-style):** Музыкальный модуль в `CtOs-Emu` работает независимо от основного ядра операционной системы, по аналогии с оптимизированными ISO-драйверами Inferno/NP9660 в кастомных прошивках PSP, обеспечивая непрерывный асинхронный стриминг данных без зависания интерфейса.

## 📱 Профили Адаптации под Аппаратные Возможности (Hardware Profiles)

Язык KITII и операционная среда CtOs динамически адаптируют свое поведение в зависимости от целевого устройства:

1.  **Профиль [DESKTOP_X86_64] (Разработка и Мониторинг):**
    *   Максимальная производительность, JIT-компиляция, неограниченное выделение памяти.
    *   Активация систем защиты ядра (`WinShield`, Anti-Debug, PEB Unlink).
    *   Отрисовка расширенного интерфейса управления (`StatusDashboard`).
    *   **БАЗА КОМПЛЕКТАЦИИ ОС — характеристики PSP-1004 Fat:** чтобы оболочка
        и ядро собирались быстро и без сюрпризов, за основу берём референс
        PSP Fat: CPU 333 МГц (MIPS R4000-класс), ОЗУ 32/64 МБ, экран 480×272,
        однозадачный Event Loop ядра, PRX-модули. Эти потолки — «гарантированный
        минимум», под который код обязан влезать всегда.
    *   **Реальное железо стенда — Acer Aspire Revo R3700 (моноблок/неттоп):**
        процессор Intel Atom D525 (1.8 ГГц, 2 ядра / 4 потока, TDP 13 Вт),
        графика NVIDIA ION 2 (чип GT218, аппаратное декодирование VP8/H.264),
        ОЗУ 1–2 ГБ DDR3 (расширение до 4 ГБ), накопитель 2.5" SATA 320–500 ГБ,
        Wi-Fi b/g/n, Ethernet 1 Гбит/с, 6× USB 2.0, VGA + HDMI, кардридер,
        оптический привод отсутствует. Для этого стенда CtOs обязана
        укладываться в реальные 2 ГБ ОЗУ и 13-ваттный термо-бюджет: это и есть
        практическая планка «ультра-легковесности» на десктопе.
    *   **Финальная проверка — установка на VM:** в конце разработки готовая
        CtOs обязана ставиться на виртуальную машину (стандартные гипервизоры:
        VirtualBox / VMware / QEMU) и подниматься там так же, как на железе —
        это контрольная точка перед выпуском, а не требование к стенду.
    *   **Хост разработки (сборка/отладка):** отдельная машина на
        Ryzen 7 5800X / B550M DS3H / 16 ГБ / GTX 1050 Ti — на ней крутятся
        компилятор стадий 2–4 и эмулятор; таргет-бинари с неё переносятся на
        стенд R3700 по сети/USB (Ethernet + кардридер).
2.  **Профиль [MOBILE_ARM32_LOWPOWER] (Тестовый стенд Samsung A10):**
    *   Жесткий лимит оперативной памяти через изолированный аллокатор `memory.ctos`.
    *   Принудительное усыпление потоков ядра для снижения частоты процессора и экономии батареи.
    *   Нативная поддержка отладочных интерфейсов USB (ADB/ADT) и сотовых сетей (3GPP).
3.  **Профиль [EMBEDDED_HARDWARE] (Микроконтроллеры и IoT):**
    *   Чистая AOT-компиляция кода KITII в машинные инструкции (ASM) без использования виртуальной машины.
    *   Прямая работа с регистрами и портами ввода-вывода (I/O) без участия сторонних операционных систем.

## 🌊 Визуальная оболочка VSH: полная копия PSP XMB

Оболочка CtOs — это **полная копия XMB (XrossMediaBar) PlayStation Portable**, собранная по референс-скриншотам официальных и кастомных прошивок. Никаких «похожих» интерфейсов — воспроизводится именно логика и вид PSP:

### Категории и навигация (как на PSP)
*   Горизонтальная лента категорий сверху: **Settings, Extras, Photo, Music, Video, Game, Network** — перемещение крестовиной/D-Pad (на тач-стенде — свайпом), выбор кнопкой подтверждения (X/Enter).
*   Под каждой категорией — вертикальный подменю-столбец с иконками и подписью выделенного пункта; подсветка и анимация прокрутки — как в оригинале.
*   Правый верхний угол: часы/дата и индикатор заряда; нижняя подсказка-кнопка возврата (`O Back` / `X 返回`).

### Экран «System Information» (копия с прошивки)
Фон — синяя волна XMB; по центру блок:
`System Software: CtOs <версия>` / `Nickname: <имя>` / `MAC Address: <адрес>` — как на скриншотах прошивок 6.35/6.60/5.50 GEN-D3/6.60 ARK-4.

### Приложение «Музыка» (CtMusic) — два режима как на PSP
1.  **Список треков:** обложка альбома/папки слева, имя трека крупно, имя исполнителя под ним, полоса прогресса и счётчик `00:41 / 04:1x` справа (референс: «The Best of Sade — Kiss of Life»).
2.  **Режим визуализатора:** чёрный фон, зелёная осциллограмма/спектр по центру, номер трека в квадратной плашке слева, название трека капсом сверху, кнопка `SHUF` снизу и полоса прогресса (референс: скриншот плеера PSP-Go).

### Терминал (системное приложение в меню)
В меню приложений **сразу под Settings** идёт **Terminal** — аналог `cmd` и `PowerShell 7.6.x`, но команды — скрипты на нашем языке KINII с понятным всем синтаксисом. Для удобства пользователя терминал принимает **команды cmd и PowerShell 7.6.7** (их имена и семантика) и транслирует их в свои вызовы. Спецификация команд: `CtOs/terminal/TERMINAL_SPEC.md`.

### Настройки: два уровня доступа
*   **Обычные настройки** — через меню Settings, распределённые по подменю (как на PSP: System Update, Video Settings, Theme Settings и т.д.).
*   **Секретные настройки** — только через `rootcmd` в терминале: команда `rootcmd: <параметр> <значение>`. Скрытые параметры не отображаются в меню вообще — их знает только владелец (регламент секретов — в TERMINAL_SPEC.md).

## 🎨 Темы оболочки: заимствованные и кастомные

Система тем — двухслойная:

### 1. Зафиксированные заимствования (базовые темы, «как на PSP»)
Эти стили берём из официальных и кастомных прошивок PSP и держим в поставке ОС как встроенные:

| Тема | Источник | Приметы |
|---|---|---|
| **XMB Classic (Original)** | официальная прошивка Sony (6.35/6.60) | синяя волна, серебристые иконки, System Information как на 6.35 |
| **ARK-4 Dark** | кастом ARK-4 / cIPL | тёмный фон меню, оранжевый акцент, «★ Custom Firmware Settings» |
| **GEN-D3 Orange** | кастом 5.50 GEN-D3 | оранжево-жёлтый градиент XMB, красные акценты |
| **Mac OS X Leopard** | кастомная тема PSP | логин-панель «Mac OS X Leopard», меню-бар Finder, док, System Preferences-сетка |

Каждая встроенная тема описывается манифестом (см. ниже) и живёт в `CtMusic/themes/builtin/`.

### 2. Папка кастомных тем (для новых тем под нашу ОС)
*   Путь: `CtMusic/themes/custom/` — **отдельная папка для кастомных тем, которые сделают уже для нашей ОС**.
*   Правило «скинул — привязалось»: пользователь кладёт папку темы в `custom/`, перезапускает оболочку (или жмёт «Обновить темы» в Settings → Theme Settings) — тема появляется в списке.
*   Переключение: **Settings → Theme Settings → <выбранная тема>** — как на PSP.
*   Формат темы и манифеста: `CtMusic/themes/README.md`.

## 📦 Дистрибутив и установка CtOs: ОС на сменном носителе (принцип PSP)

**Принцип:** скомпонованная ОС живёт на сменном носителе (SD-карта / USB) и
запускается прямо оттуда — как на PSP запускается с Memory Stick. Установочное
меню (TUI на раннем этапе / GUI в XMB: Settings → System Update) сканирует
носители, копирует ОС на внутренний диск и верифицирует образы контрольной
суммой. **Замена ОС = замена файла на карте** — никакой переустановки модулей.

После запуска ядро **автоматически монтирует** все подцепленные диски со
маршрутами `ms0:`, `ms1:`, ... (PSP-традиция) и внутренним `hd0:` — они
становятся хранилищем для всего остального: приложения, темы (правило
«скинул — привязалось» работает и с внешней карты), музыка, фото, видео, сейвы.

Детальная спецификация: `CtOs/installer/INSTALL_SPEC.md`.

### 📦 Референсный корпус PSP OS (F:\PSP_OS, анализ 2026-10)

Скачаны честные образцы реальной PSP-экосистемы: **ARK-4** (Live/Permanent CFW),
**PRO CFW 6.20** (recovery на 7 языках, включая русский), **OFW 6.61** (EBOOT.PBP,
~32.5 МБ — калибровка веса дистрибутива) и Lua-оболочка «Android» (UX-идеи берём,
путь интерпретируемой оболочки — нет, наш слой компилируется KINII).

Разбор и выводы: `CtOs/installer/PSP_REF.md`. Сводка: наши позиции
(run-from-media, «замена ОС = замена файла», System Update в XMB,
конфиг с контекстами, локализованные критические экраны, recovery отдельным
входом) подтверждены корпусом — ничего переворачивать не потребовалось.
Бинарники и материалы Sony в git не кладём: заимствуем идеи, не файлы.

## ⌨️ Спецификация подсистемы ввода (Input Hardware Devices)

Для обеспечения энергоэффективности на Samsung A10 под /e/OS ядро `kernel.ctos` не опрашивает устройства в постоянном цикле, а ожидает низкоуровневых сигналов (Hardware Interrupts). Интерпретатор `CtOs-Emu` и хуки `sys.set_hook` транслируют в ячейки памяти сигналы со следующих типов устройств ввода:

*   **Координатные и указательные интерфейсы:** Сенсорные панели экранов (Touchscreen Digitizer), стандартные мыши (USB/Bluetooth), трекпады, графические планшеты (дигитайзеры).
*   **Символьные устройства:** Физические клавиатуры (включая хук `WH_KEYBOARD_LL` для Windows-версий), виртуальные экранные клавиатуры IME, сканеры штрих-кодов/QR-кодов (эмулирующие ввод с клавиатуры).
*   **Игровые и манипуляторные контроллеры:** Геймпады (DirectInput/XInput), джойстики, рули, трекеры движения, VR-контроллеры пространственного позиционирования.
*   **Аудио- и медиа-захват:** Аналоговые и цифровые микрофоны (через подсистему аудиоэффектов смартфона), MIDI-клавиатуры и аппаратные контроллеры (передающие нотные сигналы и CC-команды).
*   **Биометрические сенсоры устройства:** Сканеры отпечатков пальцев, датчики распознавания лиц (FaceID камеры), пульсометры.
*   **Сенсоры пространственного положения (Датчики мобильного шасси):** Акселерометры, гироскопы, цифровые компасы (магнитометры), датчики приближения (Proximity Sensor), барометры.
*   **Низкоуровневые шины передачи данных и отладки:** Сигналы по USB-кабелю через мосты ADB/ADT, отладочный интерфейс UART, шины I2C и SPI (для микроконтроллеров), пакеты сотовых сетей 3GPP.

## 💾 Абсолютная системная матрица поддерживаемых форматов файлов (File System Signatures)

Язык **KITII** и низкоуровневое хранилище `sql.core` спроектированы для автономной работы со всеми существующими типами данных. Чтобы полностью исключить тяжелые сторонние библиотеки на слабом железе (вроде Samsung A10), рантайм `CtOs` осуществляет разбор файлов исключительно по их **магическим байтам (сигнатурам заголовков)** напрямую внутри сырых ячеек памяти **`cell:raw`**.

### 🎵 Аудиоформаты и контейнеры (Audio Containers & Bitstreams)

*   **Сжатие без потерь (Lossless & Uncompressed PCM/DSD):**
    *   `.wav` (Microsoft/IBM WAVE, заголовок `RIFF....WAVE`).
    *   `.aiff`, `.aif`, `.aifc` (Apple Audio Interchange, заголовок `FORM....AIFF`).
    *   `.flac` (Free Lossless Audio Codec, сигнатура `fLaC`).
    *   `.alac`, `.caf` (Apple Lossless / Core Audio Format).
    *   `.ape` (Monkey's Audio, сигнатура `MAC `).
    *   `.wv` (WavPack, заголовок `wvpk`).
    *   `.tta` (True Audio, заголовок `TTA1`).
    *   `.au`, `.snd` (NeXT/Sun Audio, сигнатура `.snd`).
    *   `.shn` (Shorten lossless audio).
    *   `.tak` (Tom's lossless Audio Kompressor).
    *   `.dsf`, `.dff` (Direct Stream Digital / Sony Super Audio CD).
    *   `.pcm`, `.raw` (Сырые беззаголовковые PCM-данные в памяти).
    *   `.ofr`, `.ofs` (OptimFROG — архивное аудиосжатие сверхвысокой плотности).

*   **Сжатие с потерями (Lossy Streaming & Mobile Codecs):**

## 📡 10. Регламент и формат совместной разработки (Core Workflow)

Для исключения рассинхронизации модулей, предотвращения конфликтов путей и защиты кодовой базы от случайного затирания, разработка экосистемы CtOs ведется строго по пошаговому инженерному регламенту:

### ⚡ 10.1. Принцип Изолированных Спринтов
*   Разработка движется строго линейно по цепочке: **Язык ➔ Компилятор ➔ Модули ОС ➔ Эмулятор ➔ Приложение ➔ Порт PSP**.
*   Запрещено одновременное написание кода из разных фаз. Текущий спринт считается завершенным только после того, как целевой файл создан в своей папке, успешно прошел синтаксический разбор и оттестирован в консоли PowerShell без вылета ошибок (Traceback).

### 🔐 10.2. Протокол Инкрементального Написания Кода
*   Все исходные коды модулей поставляются в виде чистых, готовых к компиляции листингов без использования абстрактного псевдокода.
*   Модификация существующих файлов ядра (`.ctos`, `.vc`, `.web`) производится по принципу точечного инкремента (добавления) с явным указанием целевых строк или смещений, чтобы не нарушать целостность бестипового адресного пространства `cell:raw`.

### 🧪 10.3. Цикл Отладки и Анализа Прерываний
*   Каждый созданный модуль проходит обязательный этап верификации на Windows-хосте.
*   В случае возникновения системных сбоев, аппаратных несоответствий (например, ошибок адресации чипов на плате TA-082) или ошибок рантайма, логи прерываний и дампы регистров фиксируются в папке эмулятора для проведения работы над ошибками до перекомпиляции всего ядра.

### 🗂️ 10.4. Вектор Распределения Ресурсов (Пространственная Дисциплина)
Любой новый файл проекта обязан строго соответствовать своей физической директории:
*   Грамматика, парсеры и спецификации синтаксиса Void ➔ **/Compiler**
*   Веб-интерфейсы, Frame-Buffer шаблоны и реактивный слой ➔ **/CtMusic**
*   Планировщики ядра, аллокаторы памяти и макросы команд ➔ **/CtOs**
*   Фоновые демоны, контроллеры `yt-dlp` и USB-мосты ADB/ADT ➔ **/CtOs-Emu**
*   Низкоуровневые `.prx` драйверы и MIPS-компиляторы платы TA-082 ➔ **/PSP-CtOs**

## 🏎️ 9.1. Формат работы системы и исполнения программ (Runtime Execution Flow)

Чтобы CtOs оставалась ультра-быстрой на Samsung A10 и плате TA-082, логика выполнения скриптов полностью изолирована от тяжелых системных процессов хоста и работает по строгому трехслойному циклу:

### 🌟 1. Слой Инициализации и Сценариев (.run / .ctos)
*   **Файлы сценариев (`.run`):** Текстовые или байт-кодовые файлы верхнего уровня (например, `void.run`). Они содержат инструкции запуска конкретного приложения (в нашем случае — CtMusic) и последовательность монтирования модулей.
*   **Системные модули (`.ctos`):** Низкоуровневые скомпилированные скрипты (ядро, менеджер памяти). При старте сценария `.run` диспетчер загружает `.ctos`-файлы в фиксированные адреса памяти, создавая оперативную среду CtOs.

### 🧠 2. Слой Выполнения и Контекста Памяти (Runtime Environment)
*   Когда программа встречает ключевое слово `run`, управление передается виртуальному хосту (`void_win.exe` или его мобильному ARM-аналогу).
*   Вся работа с данными происходит внутри бестипового пространства `cell:raw`. Диспетчер считывает опкоды команд, проверяет их по правилам из `compiler.core`, выполняет системные прерывания `sys_call` и мгновенно затирает память при выходе из функций (Zeroize-Exit).

### 📺 3. Слой Графического Отображения и Реактивности (.web / Rev.web)
*   **Файлы разметки (`.web`):** Содержат декларативное описание кнопок, таблиц и списков треков (наш ретро-YouTube интерфейс).
*   **Реактивный мост (`Rev.web`):** Сидит в памяти как фоновый PRX-плагин. Он не перерисовывает экран целиком. Когда низкоуровневый сетевой драйвер через `bridge.ctos` получает «паспорт» новой песни от `yt-dlp`, он генерирует аппаратный сигнал прерывания. `Rev.web` ловит этот сигнал и точечно изменяет конкретную ячейку Frame-Buffer на экране устройства, обеспечивая мгновенный отклик интерфейса без малейшей нагрузки на процессор.



## Структура Рабочего Пространства 
*   **/Compiler** — Файлы спецификации, грамматики, опкодов и синтаксического дерева языка KITII.
*   **/CtMusic** — Легковесный графический фронтенд плеера (VSH-оболочка в стиле XMB).
*   **/CtOs** — Низкоуровневые системные скрипты ядра и операционной среды. Содержит ключевые bare-metal компоненты:
    *   `firmware.ctos` — Эмулирует первичный bootloader устройства, опрашивает аппаратный профиль хоста (`#target:`) и инициализирует системную шину.
    *   `memory.ctos` — Низкоуровневый менеджер ОЗУ. Управляет распределением ячеек `cell:raw` в рамках 32 МБ оперативной памяти и контролирует Кольца Защиты.
    *   `kernel.ctos` — Главный планировщик задач и диспетчер прерываний ядра ОС (Event Loop), отвечающий за логику энергосбережения и переключение контекстов.
    *   `bridge.ctos` — Системный мост. Регистрирует криптографические NID-хеши (`sys_call`) для связи прикладного слоя с аппаратными драйверами чипов.
    *   `sql.core` — Резидентная микро-СУБД для хранения истории, кэша метаданных и цифровых подписей авторов пакетов менеджера `pinup`.
*   **/CtOs-Emu** — Среда эмуляции, рантайм-хост и сетевые драйверы прослойки.
*   **/Python_compiler** — Первичный компилятор Стадии-0 на Python (подлежит консервации в архив после сборки Стадии-1).
*   **/PSP-CtOs** — Нативный порт операционной системы и драйверов под железо PSP TA-082.
*   **/Lang_for_my_decisions-master** — Исходный код универсального диспетчера `void_win.exe` и модулей сборщика `.vc`.

## 🛡️ Архитектура Защиты Ядра ОС и Минимальные Ограничения (Core Ring Protection)

В отличие от операционной системы Android, зажимающей приложения в тяжелые виртуальные песочницы (Sandbox), в **CtOs** безопасность контролируется непосредственно на этапе компиляции и силами низкоуровневого аллокатора памяти ядра `memory.ctos`. 

Система предоставляет пользователю 99% свободы для глубокого хакинга, прямого изменения интерфейса, модификации системных скриптов и управления звуковым трактом, но жестко блокирует возможность случайно уничтожить (окирпичить) или сжечь плату.

### Физическая карта распределения ОЗУ (32 МБ фиксированного пула):
*   **КОЛЬЦО 0 (Core Ring 0): `0x00000000 - 0x00100000` (Первый 1 Мегабайт)** — Святая Святых системы. Здесь лежат Firmware, Таблица Векторов Прерываний (IVT) для опроса шлейфов кнопок и базовые таблицы дескрипторов страниц ОЗУ. Прямой доступ на запись для прикладного кода полностью заблокирован.
*   **КОЛЬЦО 1 (Core Ring 1): `0x00100000 - 0x00A00000` (9 Мегабайт)** — Системный Слой операционной системы (`kernel.ctos`, `bridge.ctos`), низкоуровневые драйверы аудио-кодека `IC4502` и контроллера питания `IC7001`.
*   **КОЛЬЦО 2 (User Ring 2): `0x00A00000 - 0x02000000` (Оставшиеся 22 Мегабайта)** — Пространство пользователя. Графическая мультимедийная VSH-оболочка, реактивные таблицы интерфейса `Rev.web` и прикладные плагины CtMusic.

### Двухуровневая фильтрация инструкций:
1.  **Статический барьер компиляции:** Если прикладной скрипт или плагин из пространства Кольца 2 пытается вызвать команду прямой записи `out_cell` в адреса ниже `0x00100000`, компилятор KITII блокирует сборку на этапе проверки AST-дерева с выводом паники: `[System Security Panic]: Writing to Protected Kernel Core Area is Forbidden`.
2.  **Динамический барьер аллокатора:** Если вредоносный или ошибочный бинарный код пытается выполнить запись в обход компилятора, функция ядра `CoreSecureWrite` в `memory.ctos` перехватывает этот вызов, увеличивает счетчик ошибок и мгновенно выбрасывает устройство в режим Kernel Panic через выделенный порт: `[Kernel Security Fault]: Access Denied to Core Ring 0`.

## 🏎️ Порядок и Хронология Ранней Загрузки ОС (Early Boot Execution Flow)

Запуск операционной системы CtOs на целевых устройствах (смартфон Samsung A10, портативная плата PSP TA-082) происходит по строгому трехэтапному каноничному Unix/Linux-сценарию. Это гарантирует максимальную информативность при отладке и исключает "слепые" зависания графической оболочки.

```text
[Включение Железа] ➔ [1. Текстовый Лог (Linux-Style)] ➔ [2. Графический Ролик (GIF/Видео)] ➔ [3. Интерфейс VSH]
```

### 📟 Этап 1: Ранний Текстовый Лог Проверки Системы (Early Boot Text Log)
*   **Логика работы:** При самом первом такте процессора скрипт `firmware.ctos` инициализирует графическую шину хоста в текстовом режиме и начинает построчно выводить моноширинный лог проверки компонентов ядра (Early Boot Output).
*   **Спецификация проверок:** На экран последовательно выводится статус верификации аппаратного профиля хоста (`#target:`), выделение пула ОЗУ фиксированного объема в `memory.ctos`, опрос межплатного шлейфа кнопок и монтирование криптографических NID-адресов драйверов звукового чипа `IC4502` в системном мосте `bridge.ctos`.
*   **Инженерная отказоустойчивость:** Никакие графические элементы на данном этапе не подгружаются. Если на плате присутствует физический дефект (например, обрыв дорожки шлейфа `6626041`), текстовый лог замирает на конкретной строке. Это позволяет мгновенно локализовать аппаратную неисправность без подключения внешних инструментов.

### 📺 Этап 2: Графический Загрузочный Ролик и Анимация (Steam Deck Style Boot Video)
*   **Логика работы:** Только после вывода финальной текстовой строки об успешной верификации всех аппаратных слоев ядра, планировщик задач `kernel.ctos` полностью очищает Frame-Buffer видеопамяти и переключает графический контроллер в нативный растровый режим.
*   **Кастомизация и формат (Стиль Steam Deck):** Загрузочный ролик не зашит намертво в BIOS. Система использует ультра-легкий и высокосжатый формат видеоконтейнера **`.webm`** (кодек VP8/VP9). Путь к медиа-ресурсу зафиксирован в конфигурационном регистре загрузчика:
    `set static Boot_Asset_Path = "system/resources/uiboot.webm";`
    Пользователь может заменить загрузочное видео в любой момент, просто перезаписав этот файл в файловой системе.
*   **Параллельные фоновые процессы:** Пока процессор через аппаратный декодер или покадровый разбор считывает бинарный поток `.webm` и копирует кадры напрямую во Frame-Buffer (диапазон `0x04000000 - 0x041FC000`), ядро в фоновом асинхронном режиме монтирует высокоуровневые сетевые демоны связи с `yt-dlp` и инициализирует таблицы локальной СУБД `sql.core`.

### 🌟 Этап 3: Передача Контекста и Старт Оболочки VSH (Visual Shell)
*   По завершении воспроизведения загрузочного ролика, кадры плавно затухают (Zeroize-Fade). Планировщик ядра `kernel.ctos` завершает загрузочный контекст, освобождает временные буферы памяти и передает управление прикладному слою — графическому интерфейсу CtMusic, отрисовываемому реактивным мостом `Rev.web` напрямую через аппаратную шину хоста.


*   **Гибридная Сенсорно-Аппаратная Матрица Ввода (Dual-Input Mapping Engine):**
    *   **Режим Сенсорного Экрана (Смартфоны / Samsung A10):** Полный отказ от дискретного пошагового переключения при работе пальцем. Графический движок XMB реализует бесшовное, гладкое перетаскивание элементов (Drag-and-Drop / Inertial Scrolling), полностью следующее за физической координатой пальца на тачскрине без рывков и задержек, в точности как нативный интерфейс Android. Быстрые свайпы (Flick-gestures) используются только для сквозной скоростной прокрутки больших массивов данных.
    *   **Режим Аппаратного Геймпада (PSP-1004 Fat / Bluetooth / USB HID):** При обнаружении подключенного контроллера (DualShock, Xbox Controller, ShanWan, Joy-Con) подсистема ввода мгновенно блокирует инерциальный тач-режим и переводит интерфейс XMB на 100% пиксельно-точную пошаговую логику управления оригинальной консоли PSP-1004 Fat (D-Pad переключает категории, геометрические кнопки управляют контекстом).

## 🧩 Appendum 2026-11: Компилятор стадии-1 (слово-язык KINII) — честная карта слот-зоны

Компилятор стадии-1: `Compiler\stage1_compiler.kt` (+ зеркало-стенд `Python_compiler\stage1_selftest.kt`),
коден стадии-0: `Python_compiler\codegen.py`, формат артефакта: контракт v1.1 (TKT-009).
Вход честный: текст = слова через пробел (`VM --source FILE.words`), упаковка 1 символ -> `ord(c)`,
2 символа -> `ord(c1) | ord(c2)<<8` ('sv' -> 0x7673, второй символ в старшем байте), '.' (0x2E) —
честный терминатор; слова кладутся в ячейки `SOURCE_CODE_BUFFER`, максимум 0x40 (64) слота
(честная вместимость 62 слова пользователя, честный брак границы 0x07).

### Честная карта ячеек слот-зоны (BE32-адреса)

| Адрес | Имя | Смысл |
|---|---|---|
| 0x00A00000 | SOURCE_CODE_BUFFER | слова исходника, <= 0x40 слотов |
| 0x3F0050C0 | LOG_PORT / OUTPUT_BINARY_PORT | честный порт лога и вывода |
| 0x00F00FF0 | STREAM_EMIT_CELL | системная: вывод артефакта (вход 'wc' НЕ выбирает) |
| 0x00F00FF1 | WORK_CELL | текущий рабочий слот W (завод честный; недостижим цифровой формой 'wc') |
| 0x00F00FF2 | FILE_EOF_CELL | системная (вход 'wc' НЕ выбирает) |
| 0x00F00FF3..0x00F00FFC | W2..WB (WC_BASE = 0x00F00FF3) | 9 именованных рабочих слотов (веха-15: W8..WB = FA..FC) |
| 0x00F00FF9 | TMP_CNT / W8 (веха-15) | системная: счётчик runtime-кольца `ml` (веха-12б) — честная двойная роль с цифрой 'wc 6' |
| 0x00F00FFA | TMP_ACC / W9 (веха-15) | системная: накопитель произведения `ml` — честная двойная роль с цифрой 'wc 7' |
| 0x00F00FFB | TMP_X / WA (веха-15) | системная: множимое (копия acc) кольца `ml` — честная двойная роль с цифрой 'wc 8' |

### Честная семантика выбора слота 'wc'

- Цифровая форма `wc d`, d из 0..9 (веха-15) -> W_Current = BE32(WC_BASE + d)
  (0x00F00FF3..0x00F00FFC); честный брак BRK_WC_NO_LIT 0x08: номера нет /
  второй 'wc' подряд (стадия-0 честно не поддерживает `<=` —
  каждый сайт-цифра честно ЗНАЕТ свою цифру по сигнатуре; ДО вехи-15 цифры
  6..9 браковались этим же кодом честно ДО эмиссии).
- Литеральная форма `nb X wc` (веха-10) — 'wc' — ЧЕСТНЫЙ ПЯТЫЙ поглотитель nb-числа: X цифрами
  отдельными словами; если X равен честному номиналу {0x00F00FF1, 0x00F00FF3..FC} -> W_Current =
  BE32(X) — АБСОЛЮТНЫЙ адрес (возврат на WORK_CELL из литерала недостижим цифровой формой);
  вне номинала — честный брак BRK_WC_RANGE 0x0D (fail-fast, поток пуст, позиция = слово 'wc');
  проверка честно развёрнута в цепь 7 равенств (static Sl_OK) — `<=` на стадии-0 нет.

### Честные поглотители nb-числа (веха-8)

Поглотители: sv, va, gp, sp, wc (BE32(Num_Acc) как операнд, без эмиссии литерала, длины эмиссий
не меняются); непоглотителей честно 12 сайтов (se, st, fu, ru, eq, gt, lt, ad, su, if, es, te —
честный брак BRK_NB_NO_CONS 0x0C при открытом числе). Цифры НЕ собираются в '12' (в стадии-0 нет
`*`/`/` — двухсимвольные литералы честно отвергаются с нулём эмиссий; честная честность модели).

### Честный обратный прыжок и умножение (вехи 12а/12б)

- `mk` — честная метка цикла: байта НЕ эмитит, `Mark_Pos = Emitted_Bytes`;
  `jb` — `OP_JMP 0x07` + `BE32(Mark_Pos + 20)` (5 Б, цель = эмиссия + 20-байтный заголовок).
  Метка одноразовая; `jb` без `mk` — брак 0x0E.
- `ml N` (N — ОДНА цифра 0..9) — честное умножение `acc := acc * N` (32-бит по модулю 2^32)
  через runtime-кольцо 92 Б: setup 25 (TMP_X←acc, CONST N, TMP_CNT←N, CONST 0, TMP_ACC←0)
  + тело 22 + body_add 39 + EXIT 6. Все цели прыжков статичны (L0 = эмиссия+25;
  JZ→L0+42, JMP→L0+81, JMP→L0+20 как эмиссионные адреса) — патч-фаза не нужна.
  `ml` байта не эмитит: ставит pending-режим `Op_Pending = 0x90`, цифра разворачивает кольцо.
  Композиция `ml 3 ml 4` = ×12 (линейно, без вложенности).
- Браки `ml`: 0x0F (множителя нет; хвост-раскладка — как 0x09, вердец 0xFF при Error=1),
  0x0C (открытое nb-число), 0x06 (два оператора подряд) — эти два fail-fast, поток пуст.
- Дизайн/факты: `Python_compiler\veha12b_design.md`; 12а — раздел «Веха-12а ФАКТ»
  в `Python_compiler\veha12_design.md`.

### Честный формат артефакта (v1.1)

артефакт = 20 Б заголовок (CTOS ver01.01 ARM32 entry 0x14 magic2 FFFFAAAA CRC32-LE)
+ эмиссия + 1 Б вердец (0xFF OK / 0xFE брак) + 24 Б отчёт (6 слов BE32: Token_Counter,
Syntax_Counter, Node_Counter, Error_Flag, Fail_Code, Fail_Position).
Длина артефакта НЕ равна эмиссии: honest arithmetic = 20 + эмиссия + 1 + 24
(например проба 97 Б = эмиссия 52 Б). Отрицательные пробы честны: fail-fast до эмиссии,
код/позиция честные, поток пуст.
