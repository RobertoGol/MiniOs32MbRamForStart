# 📦 Дистрибутив и установка CtOs: ОС на сменном носителе (принцип PSP)

Принятый архитектурный принцип: **скопированная ОС живёт на сменном носителе**
(SD-карта / USB-накопитель), устройство запускает её прямо оттуда — как на PSP
запускается с Memory Stick. Цель: лёгкость замены и работы с ОС + внешние диски
автоматом становятся хранилищем для всего остального.

## 1. Принцип «как на PSP» — запустить прямо с носителя

*   Готовый скомпонованный бинарь CtOs кладётся на SD/USB-карту — установка
    на устройство **не обязательна**: bootstrap стадии-0 на устройстве читает
    носитель и ядро исполняется сразу оттуда.
*   Честное уточнение по железу: карта по шине медленнее ОЗУ, поэтому
    в реальности bootstrap честно загружает ядро во staging-область ОЗУ
    (Ring 1) и исполняет оттуда — но носитель остаётся источником правды
    (все файлы читаются с карты, как `ms0:` на PSP).
*   Два пути:
    1.  **Run-from-media** (PSP-стиль): носитель вставлен → загрузился → ОС
        с носителя. Замена ОС = замена файла на карте.
    2.  **Установленный** (для R3700): ОС скопирована на внутренний HDD
        через установщик; носитель потом свободен для хранилища.

## 2. Установочное меню (первое меню устройства)

Загрузчик стартует мини-прошивку CtOs BIOS с честным выбором источника:

*   **TUI-режим** — на раннем этапе загрузки и на слабых стендах (PSP-база
    32 МБ): текстовое меню, честное по ресурсам.
*   **GUI-режим** — после загрузки VSH XMB: **Settings → System Update →
    «Установка ОС с носителя»** — в стиле PSP System Update.

Меню делает:
1.  **Скан носителей** — SD-слот, USB-порты, SATA-накопитель; список
    найденных CtOs-образов с честной версией из заголовка (`version`,
    `target`, контрольная сумма).
2.  **«Скопировать ОС»** — копирование выбранного образа на целевой диск
    (внутренний HDD или другая карта), затем **верификация суммой**;
    битый образ честно отказывается ставиться (ошибка в меню, не паника).
3.  **«Загрузиться отсюда»** — выбрать источник загрузки на этот раз
    (носитель или установленный диск).
4.  **Журнал** — каждая операция пишется в `.log`: время, источник,
    цель, результат, CRC.

## 3. Облегчение замены: смена ОС = замена файла

*   Новая версия ОС: заменил файл на карте → перезапуск → новая версия.
    Никаких переустановок модулей и драйверов.
*   Версионирование в заголовке бинаря честное: старый и новый образ могут
    лежать рядом на карте; установщик показывает обе версии и позволяет
    откатиться (скопировать старую обратно).
*   Пользовательские данные (темы, музыка, сейвы) на установочном образе
    не живут — только в хранилищах (п. 4), поэтому смена ОС их не трогает.

## 4. Автоподхват дисков: внешние карты = хранилище всего

После загрузки ядро (`bridge.ctos` + `memory.ctos`) честно перечисляет все
порт-диски (USB / SD-слоты / SATA) и **автоматически монтирует** каждый
подцепленный носитель:

*   Каждому привязывается маршрут по порядку обнаружения: `ms0:`, `ms1:`,
    `ms2:`... (PSP-традиция Memory Stick), внутренний HDD — `hd0:`.
*   Смонтированные диски становятся **хранилищем для всего остального**:
    приложения, темы (`themes/custom/` — «скинул на карту — привязалось»
    работает и с внешнего диска), музыка, фото, видео, сейвы, скрипты
    терминала.
*   Отключение носителя в момент записи — честная ошибка ОС пользователю
    (ядро завершает задачу записи), данные другого диска не затрагиваются.
*   Права честные: в системный раздел пишет только установщик/ядро;
    прикладные задачи Ring 2 пишут только в смонтированные хранилища.

## 5. Порядок работы спринтов

1.  Формат образа на диске (заголовок CTOS + CRC) — уже есть основа в
    контракте байткода.
2.  TUI-установщик (стадия-0, честные команды меню) — после спринтов
    планировщика.
3.  Автоэнумерация дисков + маршруты `ms0:`/`hd0:` в `bridge.ctos`.
4.  GUI-установщик в XMB (Settings → System Update).

## Статус
Спецификация. Реализация — после ядра и планировщика (Этап 3), в спринте
прикладного слоя (TUI — вместе со Спринтом Терминала).
