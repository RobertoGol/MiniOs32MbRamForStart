# CtOS — честный план вывода на железо (bring-up)

Статус: 🟡 спека/план (2026-11-08). Связан: [[TKT-031_vm_final_check]], [[TKT-055]], [[TKT-042]], [[TKT-025_installer_tui]].

## 1) Честная текущая реальность

- Логика ядра/ОС пишется на KINII (стадия-0) и компилируется Python-стадийным `codegen.py` в байткод **`.ctos`** (формат v1.1, заголовок 16 Б `CTOS` + LE поля, entry, BE32 аргументы опкодов). Исполнение сейчас — **`CtOs-Emu/ctos_vm.py`** (интерпретатор на Python, Windows-хост).
- Готовые/проверенные на VM компоненты (2026-11-08): `CtOs/memmgr.kt/.ctos` (аллокатор с привязкой к задаче, ledger, zeroize-exit, honest bounds, маркеры 0xA7xx, VM exit 0); `CtOs/kernel_sched.kt/.ctos` (Task-таблица 0x00A10000, 32 слота, ready-очередь, spawn/dispatch-state/yield-state/exit→ZOMBIE, браки 0xF1/0xF2, маркеры 0xB6xx, VM exit 0). Контекстный NID 0x150–0x152 **не реализован** (конфликтное окно 12в/12г) — реальный прыжок в entry/переключение контекста отложен честно.
- **Следствие:** «ОС работает сразу на железе» НЕ достигается копированием `.ctos` на голое железо. Нужен слой исполнения/загрузки ниже байткода. Это честный разрыв, не баг.

## 2) Цели железа (HANDOFF)

| Цель | Профиль | Роль | Честная сложность bring-up |
|---|---|---|---|
| VM (VirtualBox/VMware/**QEMU**) | x86/x64 гостевая машина | **финальная приёмка** (TKT-031) | средняя — стандартный boot (GRUB/multiboot/UEFI) + нативный рантайм |
| Acer Aspire Revo R3700 | Intel Atom D525, ION2, 1–2 ГБ, 13 Вт | реальный стенд | средняя — x86, похож на VM/QEMU путь |
| PSP-1004 Fat | MIPS Allegrex, 32/64 МБ, кастомный IPL/шлейфы | гарантированный минимум по спекам | высокая — зависит от цепочки прошивки/загрузчика (см. TKT-042 «прямая зависимость»); отдельная веха |

Приоритет практического bring-up для «заработало на железе»: **QEMU x86 → R3700 (x86)**, параллельно готовя код к малой памяти/портируемости; PSP — отдельным треком через TKT-042/045.

## 3) Варианты слоя исполнения (выбрать честно по вехам)

### Вариант A — Нативный интерпретатор `.ctos` (рекомендуемый первый шаг)
- Переписать ядро `ctos_vm.py` как **малый нативный рантайм** (C/asm или KINII freestanding, когда готов) с тем же контрактом опкодов/NID и картой ячеек.
- Плюсы: переиспользуем весь существующий `.ctos`/компилятор/пробы без переписывания ОС; минимальный риск регрессий семантики. Минусы: накладные расходы интерпретации (на Atom/13 Вт приемлемо для ядра/оболочки? мерить честно), нужен boot shim.
- Вехи: A1 минимальный интерпретатор опкодов, уже используемых ядром (без полного набора) + ячейки памяти + out/log; A2 NID-слой (файлы/контекст 0x150–152) через HAL; A3 загрузка `.ctos`-модулей ядра.

### Вариант B — AOT/нативный бэкенд (цель)
- Генерация нативного кода (x86 для QEMU/R3700; MIPS для PSP-трека) из `.kt` или из `.ctos`. Честно дорого; после стабилизации семантики и когда freestanding-бэкенд KINII созреет.
- Веха: B1 backend для подмножества опкодов ядра, сверка поведения с эталоном `.ctos` на VM.

### Вариант C — Гибрид (прагматично)
- Критичный путь (boot, irq/таймер, диспетчер, HAL портов) — нативный; прикладные/сервисные модули — `.ctos` под интерпретатором A.

## 4) Аппаратная абстракция (HAL) — обязательна для «сразу на железе»

Текущий код обращается к портам/ячейкам как к константам (на VM `cells.get` отдаёт 0 для unmapped — безопасно, но не железо). Нужен явный HAL-слой:

- **Память:** обнаружение/конфиг размера RAM; маппинг Ring 0/1/2 (`0x00000000/0x00100000/0x00A00000`) адаптируется к реальной карте (не хардкодить 32 МБ как истину для R3700). `memmgr` уже честно ограничен HEAP_BASE/END — вынести границы в конфиг/параметры init.
- **Таймер/IRQ:** вытеснение (TKT-055 спринт Б) и No-HZ требуют источника тиков; на x86 — PIT/APIC/HPET (минимум), на PSP — свой таймер. Сейчас только кооперативная модель состояний.
- **Ввод/вывод:** ранний лог (serial/VGA text на x86; шина/дисплей на PSP), хранение (диск/образ), сеть — через HAL/NID.
- **Контекст задачи:** NID 0x150–152 в VM; на железе — нативный save/restore регистров + стек (ABI целевой архитектуры).

## 5) Фазы (конкретные, проверяемые)

1. **Ф0 (сейчас, VM, без конфликтов с 12в/12г):** ядро-состояния и память готовы/проверены (`memmgr`, `kernel_sched`); спека bring-up зафиксирована; VM NID 0x150–152 отложены до свободного окна. ✅ частично.
2. **Ф1 (VM, свободное окно):** адитивные NID 0x150–152 в `ctos_vm.py` + Ф-А1/А2/А3 TKT-055; регресс существующих `.ctos`/проб стадий байт-в-байт.
3. **Ф2 (нативный рантайм, x86):** минимальный интерпретатор `.ctos` подмножества + загрузка `kernel_sched.ctos`/`memmgr.ctos` в QEMU (multiboot/GRUB или сырой загрузчик), вывод лога на serial/VGA text.
4. **Ф3 (QEMU→R3700):** таймерный тик + вытеснение/No-HZ, блочное устройство/образ, установщик (TKT-025) на виртуальный/реальный диск.
5. **Ф4 (приёмка, TKT-031):** установка на VM-диск, загрузка, bootlog, No-HZ честный в простое; чек-лист приёмки закрыт.
6. **Ф5 (PSP-трек, отдельно):** по TKT-042/D1–D5, с учётом лицензионной честности и цепочки загрузки PSP.

## 6) Критерии честности

- Не заявлять «работает на железе», пока бинарь не загрузился и не прошёл чек-лист на реальной цели (QEMU считается VM-целью приёмки по TKT-031).
- Любая деградация (нет таймера, нет диска, только кооперативный режим) — явный флаг/лог, не тихое поведение.
- Адреса/размеры памяти — конфигурируемы; 32 МБ — минимум/профиль, не глобальная константа для всех целей.
