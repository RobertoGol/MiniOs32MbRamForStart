# 🧵 Многопоточность CtOs: модель как в Linux, код — наш

Всё ядро многопоточности пишется на KINII (`kernel.ctos` + `memory.ctos`) —
никакого чужого кода. У Linux берём **семантику** (задачи, вытеснение,
приоритеты, futex-подобная синхронизация), реализация — своя, под наш бинарь.

## 1. Задача (task) — базовая единица
Как в Linux: задача = поток исполнения со своим контекстом.

```
struct Task (kernel.ctos):
    tid: u32            // уникальный номер задачи
    state: u8           // READY / RUNNING / SLEEPING / WAITING / ZOMBIE
    prio: i8            // nice: -20 (самый важный) .. +19 (фоновая)
    vruntime: u64       // «наработанное время» для честности планировщика
    stack_top: u32      // вершина стека задачи (адрес в cell:raw)
    context: [16] u32   // снимок регистров для переключения
    wait_queue: u32     // на какой очереди спит (0 = нигде)
    parent: u32         // кто породил (для join)
```

Разновидности:
*   **Ядерные задачи (kthread)** — фоновые демоны ОС (сетевой демон, драйвер
    аудио, планировщик «прожарки» тем) — живут в Ring 1.
*   **Прикладные задачи** — потоки приложений CtMusic и плагинов — Ring 2.
*   **idle-задача** — всегда существует; когда больше нечего исполнять,
    ядро уходит в `sys_call sleep` (энергосбережение из Readme).

## 2. Планировщик (kernel.ctos) — вытесняющий, честный
*   **Вытеснение по таймеру**: аппаратный таймер даёт прерывание кванта
    (по умолчанию 10 мс, настраивается `rootcmd: sched.quantum <мс>`).
    По прерыванию планировщик сохраняет контекст текущей задачи и выбирает
    следующую — задача не может «зависнуть» ядро навсегда.
*   **Честность как в CFS (упрощённо честно)**: у каждой задачи `vruntime`
    нарабатывается; следующей исполняется задача с наименьшим `vruntime`
    среди готовых. Приоритет `nice` меняет скорость наработки: чем выше
    приоритет, тем медленнее растёт vruntime → чаще выбирается.
    (Без красно-чёрных деревьев Linux — на 32/64 МБ ОЗУ держим очереди
    по 32 приоритетным группам: O(1) выбор, честность через vruntime.)
*   **Усыпление**: `sleep(мс)` переводит в SLEEPING с таймером пробуждения;
    `yield()` — добровольно отдаёт квант.
*   **Энергоэффективность (Samsung A10 / R3700)**: если готовых задач нет,
    планировщик гасит такты (idle → deep sleep) вместо холостого опроса.

## 3. Системные вызовы потоков (NID-таблица bridge.ctos)

| Вызов KINII | Смысл (аналог Linux) |
|---|---|
| `task.spawn(fn, stack)` | `clone()` — породить задачу от функции |
| `task.join(tid)` | `wait4()` — дождаться завершения |
| `task.exit(code)` | `exit()` — завершить текущую задачу |
| `task.yield()` | `sched_yield()` |
| `task.sleep(мс)` | `nanosleep()` |
| `task.nice(tid, n)` | `setpriority()` |
| `mutex.lock(m)` / `mutex.unlock(m)` | `futex(FUTEX_LOCK/UNLOCK)` |
| `mutex.wait(m)` / `mutex.wake(m)` | `futex(FUTEX_WAIT/WAKE)` |

В языке KINII это поднимается конструкциями `node`/`isolate` (уже есть в
компиляторе kinic: на хосте они ложатся на потоки ОС-хоста, в CtOs — на
задачи планировщика).

## 4. Синхронизация и память
*   **Мьютекс** = спин-попытка (малое число итераций) → сон на очереди
    мьютекса (как futex в Linux). Никаких вечных спинов на 13-ваттном CPU.
*   **Правило memory.ctos**: аллокатор выдаёт ячейки с привязкой к задаче;
    при завершении задачи (ZOMBIE → зачистка) её недовозвращённые ячейки
    освобождает ядро (Zeroize-Exit из Readme) — утечка одной задачи не убивает
    систему.
*   **Защита ядра**: прикладная задача из Ring 2 не может вызвать
    `mutex.*` на адресах Ring 0/1 — честная ошибка компиляции (статический
    барьер) или Kernel Panic от `CoreSecureWrite` (динамический барьер).
