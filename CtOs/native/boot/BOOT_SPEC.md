# A3b/A4a/A5 — сырой legacy-BIOS загрузчик, нативный рантайм и самоустановка CtOS (эмуляционная контрольная точка)

Статус: ✅ A3b, ✅ A4a и ✅ A5 приняты **в QEMU** (2026-11-18/19). ❌ **На железе не принято**: доступа к Acer Aspire Revo R3700 нет, моноблок без интернета. QEMU ставился только на хосте (`winget`, `SoftwareFreedomConservancy.QEMU` 11.1.0) как эмуляционная контрольная точка и **не заменяет** приёмку на моноблоке. UEFI/GRUB на целевой машине не подтверждены; путь — только legacy BIOS. Моноблок пока не трогаем.

Связано: `CtOs/BRINGUP_SPEC.md` (Ф2/Ф3), `CtOs/native/NATIVE_RT_SPEC.md`, `Python_compiler/verify_boot_image.py`, `Python_compiler/verify_a5_install.py`.

## 1) Что реально исполняется

Полный путь без псевдокода и без заглушек:

1. **MBR** (LBA 0, entry `0x7C00`, 188 Б кода + сигнатура `55 AA`). Проверяет EDD через `INT 13h AH=41h` (`BX=55AA` → `BX=AA55`, `CX bit0`), затем `INT 13h AH=42h` читает 4 сектора stage2 в `0x1000:0000` и передаёт управление `ljmp $0x1000,$0`.
2. **Stage2** (LBA 1..4, 1392 Б). Инициализирует COM1 (115200 8N1), печатает `CTOS A3b STAGE2` в VGA text и COM1, повторно проверяет EDD (номер диска берётся из сохранённой переменной — `INT 10h` портит `DL`), читает 64 сектора CTMD с LBA 8 в `0x2000:0000`.
3. **A5-установщик** (LBA 5..7, 1188 Б, `0x5000:0000`). Stage2 вызывает его **только** при маркере `CTOS-INST-A5` в LBA0+`0x180` (иначе LBA 5..7 — нули, звать их нельзя). Установщик сканирует диски `0x80..0xEF` через EDD, ищет маркер `CTOS-TGT-A5!` в MBR+`0x180`, копирует 136 секторов образа с перечиткой и сравнением `repe cmpsb`, ставит `ACTIVE=0x80` в MBR+`0x1BE`, пишет sentinel `CTOS-LOCK-A5` в LBA136 (версия=1, `image_sectors=136`, CRC-32 сумма dword LBA0..135, флаги=0), снимает оба маркера и затирает LBA5..7. Коды возврата в `AL`: 0 — установки нет, 1 — установлено, 2 — честный отказ. При отказе stage2 печатает `CTOS A5 REFUSED` и выдаёт `AX=0x12` (rc=37).
4. Проверяет magic `CTMD`, версию/число модулей, каталог (48 Б на запись), границы тела и CRC-32 каждого из 4 модулей. Печатает имя и `CRC OK` / `CRC FAIL`; при браке — `CTMD FAIL` и отказ `AX=0x11`.
5. **A4a-загрузка PM**: EDD `AH=42h` читает 64 сектора с LBA 72 в `0x4000:0000` (физ. `0x40000`). Отказ чтения — `AX=0x11`.
6. **Защищённый режим**: `lgdt`, `cli`, `CR0.PE=1`. Переход в PM-рантайм — явный 32-битный far jump `EA <offset32> <sel16>` на линейный адрес `0x40000` (селектор `0x08`). Два честных бага найдены трассой QEMU `-d in_asm,int` и исправлены:
   - 16-битная форма `EA` уходила по VMA-метке в `0x50000` (метки stage2 имеют VMA 0, но исполняются по `0x10000`);
   - префикс `0x66` в `.code32` переключает far jump в 16-битный вариант, поэтому в `.code32` нужен **голый** `EA`.
7. В PM `_start` (`pm_start.S`) ставит плоские CS/DS/ES/SS, стек `0x90000`, обнуляет BSS по линкерным символам `_bss_start`/`_bss_end` (BSS по `0x01000000`, вдали от стека и VGA `0xB8000`) и вызывает `_main(5, argv)` с argv `native_rt --module memmgr CTMD:image events:com1`.
8. **Тот же `CtOs/native/native_rt.c` без правок семантики** компилируется в flat 32-bit PM-код с `-ffreestanding -nostdinc -mno-mmx -mno-sse -mno-sse2` (иначе GCC выдаёт `pcmpeqd %xmm3,%xmm3` и QEMU падает `#UD` при `CR4=0`). `pm/shim.c` подменяет **только libc**: `FILE` в памяти для CTMD и артефактов, COM1 для event'ов и `FATAL`, bump-allocator, минимальный `snprintf`/`fprintf`. Символов `nm -u` в PM-рантайме нет — builder это проверяет.
9. Успех `main()==0` ⇒ `isa-debug-exit AX=0x13` (rc=39). Отказ `verify_code()` / `fatal()` ⇒ `exit(1)` ⇒ `AX=0x14` (rc=41). COM1-лог после `CTOS A4a EXEC` байт-в-байт совпадает с хост-запуском `native_rt.exe --module memmgr`.

## 2) Раскладка образа (512 Б/сектор, всего 136 секторов = 69632 Б)

| LBA | Содержимое | Адрес исполнения/загрузки |
|---|---|---|
| 0 | MBR: 188 Б кода + `55 AA` | `0x7C00` |
| 1..4 | stage2 (4 сектора, 1392 Б из 2048) | `0x1000:0000` (физ. `0x10000`) |
| 5..7 | A5: 16-битный установщик (1188 Б из 1536) | `0x5000:0000` |
| 8..71 | CTMD v1: 64 сектора, 28425 Б | `0x2000:0000` (физ. `0x20000`) |
| 72..135 | A4a PM-рантайм: 64 сектора, 21220 Б | `0x4000:0000` (физ. `0x40000`) |
| 136 | sentinel закрепления (в образ НЕ входит, пишется установщиком на цели) | — |

Образ и промежуточные `*.bin` в VCS не идут: `build_boot_image.py` воспроизводит их из `mbr.S` / `stage2.S` / `install.S` / `pm/` / CTMD.

## 4) Коды `isa-debug-exit` (только QEMU-хук, не часть железа)

| AX | rc QEMU | Смысл |
|---:|---:|---|
| `0x10` | 33 | старый A3b-успех: PM достигнут, VGA прочитан, `PM OK` в COM1; больше не основной путь |
| `0x11` | 35 | честный отказ stage2 (нет EDD / read fail / magic / CRC / CTMD FAIL / PM read fail) |
| `0x12` | 37 | честный отказ MBR (нет EDD / read fail) или A5 (нет цели / сбой записи) |
| `0x13` | 39 | успех A4a: PM-рантайм отработал, event-лог совпал с хостом |
| `0x14` | 41 | runtime-fatal: `verify_code()` / `fatal()` / `exit(1)` внутри PM-рантайма |

Верификатор удаляет лог перед каждым запуском и строит в отдельном TEMP-каталоге. Имя лога — `serial.log`, **не** `com1.log`: на Windows `COM1` — зарезервированное имя устройства, `os.remove` по такому пути падает с `WinError 5`. Перед каждым хост-запуском удаляется `<binary>.out`.

## 6) Честные границы

- QEMU — эмуляционная контрольная точка. «Заработало на R3700» **не заявляется**: реальной загрузки с диска на моноблоке не было.
- `isa-debug-exit` — тестовый хук QEMU, на железе он не завершает машину честно; для реального стенда нужен отдельный путь завершения/передачи управления ядру.
- A4a исполняет **только `memmgr`** в PM. Остальные модули CTMD (`sched`, `syscall_test`, `stage1`) проверены по CRC в stage2, но в PM не запускались; полная самосборка `S(S_T)` остаётся хостовым A1/A2/A3a-гейтом.
- A4a меняет только libc-окружение: семантика `native_rt.c` не тронута, в PM нет настоящей файловой системы, прерываний и HAL физической памяти.
- MBR-отказ `rc=37` запрограммирован, но в автоматический верификатор не включён: автоматически проверяются magic/CRC-негативы stage2 и runtime-fatal.
- A5 проверен только в QEMU с двумя raw-дисками: источник с `CTOS-INST-A5`, цель с `CTOS-TGT-A5!`. На R3700 установка **не проводилась** — моноблок пока не трогаем.
- A5 не шифрует диск: на R3700 нет TPM/надёжного ключа. «Закрепление загрузки» = `ACTIVE` в MBR + sentinel в LBA136 + самоудаление установщика, а не криптография.
- A5 запускает тот же уже проверенный `memmgr` из CTMD (первый вариант, к которому склонялся владелец); новый модуль не вводится.
