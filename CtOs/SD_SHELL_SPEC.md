# SD Shell Spec (черновик)

Дата: 2026-11-21  
Статус: черновик, не реализовано.  
Цель: зафиксировать модель “SSD — основная система, SD — съёмная библиотека/оболочка с приоритетом при подключении”.

## 1. Цель

- Основная CtOS установлена на SSD.
- SD-карта используется как съёмный носитель данных/модулей (игры, сборники, моды, видео, фото, ИИ-данные и т.п.).
- При подключении SD система сканирует носитель и ищет “оболочку” (наш аналог PSP-shell).
- Если на SD найдена валидная оболочка, она имеет **приоритет** перед резервной оболочкой на SSD.
- На SSD хранится **резервная оболочка** в служебной области подсистемы; обычный пользователь не должен иметь к ней прямой доступ.
- Пользователь может выборочно переносить/копировать элементы с SD на SSD через GUI (для каждой игры/элемента отдельно).

## 2. Текущее состояние (честно)

- Есть: A1–A14 boot/PM/CTMD/A5 install/A14 name/name_sep в QEMU; физическая инвентаризация R3700.
- Нет: hotplug-обработки SD, GUI-менеджера, индекса ссылок, защищённой пользователь-недоступной области, формата манифеста SD-оболочки, fallback-рантайма, модели копирования “по игре”.

## 3. Термины

- **Главный диск (SSD)** — диск с установленной CtOS, системными модулями, резервной оболочкой и локальными данными.
- **SD-библиотека** — съёмный диск/карта с манифестами контента и опциональной оболочкой.
- **Оболочка (shell)** — UI/launcher CtOS, запускаемый как пакет/модуль. Формат по умолчанию: пакет с манифестом + полезная нагрузка (`.ctos` модуль или нативный модуль, формат уточняется при реализации).
- **Резервная оболочка** — доверенная локальная копия оболочки на SSD, используемая при отсутствии/ошибке SD-оболочки.
- **Манифест** — небольшой файл метаданных, описывающий оболочку или элемент библиотеки.

## 4. Модель доверия (решение пользователя)

- **Обязательная криптоподпись SD: OFF по умолчанию.** Пользовательское устройство, без требования PKI/Sony-подобной подписи.
- **Риск:** любой код/повреждённый образ на SD может быть запущен, если он распознан как оболочка. Это осознанный компромисс.
- **Опционально (не обязательно):** локальный хэш/allowlist/пометка “доверять этой оболочке” при первом запуске; журнал изменений.

## 5. Структура SD (предложение)

Корень SD содержит каталог `CTOS/` (имя предварительное):

```text
/CTOS/
  SHELL/
    shell.manifest
    shell.ctos            (или другой payload)
    assets/...
  LIBRARY/
    <item-id>/
      item.manifest
      content/...
  INDEX/
    cache.db              (опционально, пересоздаваемый)
```

Правила:
- Сканирование ищет только известные пути/манифесты, не выполняет произвольные файлы.
- При отсутствии `CTOS/` SD считается обычной библиотекой/носителем данных.
- Повреждённый манифест не должен вызывать падение системы; ошибка логируется, элемент пропускается.

## 6. Манифест оболочки (черновик)

`CTOS/SHELL/shell.manifest` (формат: текстовый ключ=значение или JSON; выбрать один при реализации):

| Поле | Обяз. | Описание |
|---|---:|---|
| `format` | да | Версия формата манифеста, напр. `ctos-shell-1` |
| `id` | да | Идентификатор оболочки |
| `name` | да | Имя для UI/лога |
| `version` | да | Версия оболочки |
| `min_ctos` | да | Минимальная совместимая версия CtOS |
| `payload` | да | Относительный путь к payload (`shell.ctos` и т.п.) |
| `entry` | нет | Точка входа/тип запуска |
| `hash` | нет | Хэш payload для опциональной проверки целостности |

## 7. Манифест элемента библиотеки (черновик)

`CTOS/LIBRARY/<item-id>/item.manifest`:

| Поле | Обяз. | Описание |
|---|---:|---|
| `format` | да | `ctos-item-1` |
| `id` | да | Стабильный ID элемента |
| `type` | да | `game`, `mod`, `video`, `photo`, `ai`, `app`, `other` |
| `name` | да | Отображаемое имя |
| `version` | нет | Версия |
| `size` | нет | Размер/оценка |
| `installable` | нет | Можно ли копировать на SSD |
| `content` | да | Относительный путь к данным |

## 8. Приоритет запуска/обнаружения

### При загрузке системы
1. Проверить наличие съёмной SD.
2. Если SD есть — просканировать `CTOS/SHELL/shell.manifest`.
3. Если оболочка валидна по формату/совместимости — запустить SD-оболочку (приоритет).
4. Иначе — запустить резервную оболочку с SSD.
5. Любое решение логировать: источник, версия, причина fallback.

### При горячем подключении SD (hotplug)
1. Обнаружить вставку SD.
2. Выполнить read-only scan манифестов.
3. Обновить индекс меню/ссылок.
4. Если текущая оболочка — резервная, предложить/выполнить переключение на SD-оболочку по политике (политика уточняется: авто-переключение или подтверждение).
5. При извлечении SD — убрать ссылки на недоступные элементы, сохранить состояние.

## 9. Резервная оболочка на SSD

- Хранится в служебной области подсистемы на главном диске.
- Не должна быть доступна обычному пользовательскому UI как обычный файл для редактирования/удаления.
- Обновляется только системным механизмом обновления/установки.
- Имеет версию и журнал; используется как fallback по умолчанию.

Реализация “недоступности пользователю” зависит от модели безопасности CtOS; на раннем этапе минимум — отдельный служебный раздел/образ + проверка целостности при загрузке.

## 10. Копирование на SSD (GUI, будущее)

- Для каждого элемента библиотеки пользователь может выбрать: “только ссылка с SD” или “копировать на SSD”.
- Копирование должно быть атомарным/возобновляемым (по возможности), с проверкой места и целостности.
- После копирования меню может показывать источник: `SD` / `SSD` / `оба`.

## 11. Логирование и диагностика

- Логировать: обнаружение SD, результат scan, выбранную оболочку, версию, fallback, ошибки манифеста, операции копирования.
- Лог не должен содержать лишние персональные данные; пути/ID элементов — допустимы.

## 12. Ограничения и открытые вопросы

1. Точный формат оболочки: `.ctos`, нативный бинарник, или пакет?
2. Политика hotplug-переключения: автоматически или с подтверждением?
3. Как определяется “служебная область, недоступная пользователю” в текущей модели CtOS без полноценной user isolation?
4. Нужен ли минимальный integrity check (hash) по умолчанию, несмотря на отсутствие подписи?
5. Как обрабатывать конфликт версий: SD старее/новее резервной?
6. Формат индекса/кэша на SD: пересоздавать всегда или переиспользовать?
7. Поведение при плохой SD (I/O errors): таймаут, quarantine, только fallback.
